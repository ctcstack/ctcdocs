# Local development

Two different things are called local development here, and they need different
commands: working on the platform, and working in a project that installs it.

## Working on the platform

Requirements are the Node.js version in `.node-version`, the pnpm version in the
root `package.json`, and Git. Nothing is needed globally; every tool is locked in
`pnpm-lock.yaml`.

```bash
corepack enable
pnpm install
pnpm --filter ctcdocs-fixture-project exec playwright install --with-deps chromium
pnpm verify
```

| Command                | Purpose                                                                  |
| ---------------------- | ------------------------------------------------------------------------ |
| `pnpm verify`          | The canonical gate. Everything below, in order, plus formatting and lint |
| `pnpm build`           | Compile the three packages. `prepack` runs this too                      |
| `pnpm typecheck`       | Types across the workspace                                               |
| `pnpm test`            | Unit, property and fixture tests                                         |
| `pnpm test:coverage`   | The same with coverage                                                   |
| `pnpm fixtures:check`  | Regenerate the fixture corpus and fail if a byte moved                   |
| `pnpm fixtures:build`  | Build the fixture project                                                |
| `pnpm fixtures:ux`     | Accessibility and interface checks against the fixture project           |
| `pnpm fixtures:search` | Pagefind acceptance against the fixture project                          |

`fixtures/project/` is a complete CTCDocs project with a synthetic corpus. It is
what the gate exercises, and the fastest way to see a change end to end: edit a
package, run `pnpm verify`, read the result in a real site.

No Google credentials are required. The fixture corpus is generated by driving
the real pipeline over sanitized HTML fixtures, so conversion changes show up
without touching a Drive.

## Working in a project

A project installs `@ctcstack/ctcdocs` and `@ctcstack/ctcdocs-sync` and runs the
commands they provide. Its `package.json` scripts wrap them; the names below are
the ones the reusable workflows call.

| Command                                            | Purpose                                                       |
| -------------------------------------------------- | ------------------------------------------------------------- |
| `astro dev`                                        | Development server                                            |
| `astro check && astro build`                       | Type-check and build the static site                          |
| `ctcdocs-sync validate`                            | Check configuration, content and deployment invariants        |
| `ctcdocs-sync sync --dry-run`                      | Export, convert and stage without writing                     |
| `ctcdocs-sync sync`                                | Replace generated output after validation                     |
| `ctcdocs-sync sync --full`                         | Force re-export of every selected document                    |
| `ctcdocs-sync sync --file <id>`                    | Re-export one document without unrelated deletion             |
| `ctcdocs-sync sync --reseed-slug <id>`             | Change one stable URL and leave a redirect behind             |
| `ctcdocs-verify-search`                            | Exercise the built Pagefind index                             |
| `ctcdocs-access-smoke --preflight`                 | Prove the boundary before deploying                           |
| `ctcdocs-access-smoke --post-deploy`               | Prove the deployed surface answers as its visibility declares |
| `playwright test --config playwright.ux.config.ts` | Accessibility and interface checks                            |
| `wrangler deploy --env production --dry-run`       | Validate the deployment target without uploading              |

Add `--json` to a sync command only when a report containing file names and
paths is appropriate for the security context you are in. The normal log carries
counts and issue categories.

## Environment

Secrets and addresses are environment variables, read from an ignored `.env` in
the project root. Never put access tokens, Drive identifiers, credentials or
exported content into documentation or fixtures.

Synchronization:

```text
GOOGLE_DRIVE_ID
GOOGLE_ROOT_FOLDER_ID
GOOGLE_IGNORED_FOLDER_IDS
GOOGLE_ACCESS_TOKEN
SYNC_SITE_BASE_URL
```

`GOOGLE_ACCESS_TOKEN` must be short-lived. The supported path obtains it in CI
through Workload Identity Federation, and the pipeline never reads a
service-account key file — see
[GOOGLE_WORKSPACE_SETUP.md](GOOGLE_WORKSPACE_SETUP.md).

The access smoke test:

```text
CTCDOCS_BASE_URL
CF_ACCESS_CLIENT_ID
CF_ACCESS_CLIENT_SECRET
```

Deployment, which Wrangler reads from its own `.env` in the directory holding
`wrangler.jsonc`:

```text
CLOUDFLARE_ACCOUNT_ID
CLOUDFLARE_API_TOKEN
```

Keep deployment credentials out of a normal development environment. A project's
gate only ever runs `wrangler deploy --dry-run`, which uploads nothing; real
deployments go through the protected workflows in
[DEPLOYMENT.md](DEPLOYMENT.md).

## Generated paths

The pipeline may write only the paths declared in
`packages/core/src/project-layout.ts`. It stages a complete tree, validates it,
and replaces the generated targets atomically, so a failed run leaves the last
known-good output untouched. The allowlist is a compile-time constant and is not
configurable: an allowlist a project can widen is an allowlist an attacker can
widen. Do not add files to generated directories by hand.
