# Starting a new project

An ordered path from an empty repository to a deployed documentation site.

It is deliberately in two halves. Everything in **Part 1** you can do alone, in
an hour, and it ends with the site running on your machine against placeholder
content. **Part 2** needs a Google Workspace administrator and a Cloudflare
account, and it is where the waiting happens — so read Part 2 first and start
asking for what it needs before you begin.

`fixtures/project/` in this repository is a working project with a synthetic
corpus. Every file below exists there; when a snippet here is shorter than the
real thing, that is the copy to take.

## Part 1 — a site on your machine

### 1. Create the repository and install

Your documentation is not public, even when the site is. The repository holds
the generated corpus, so it is private.

```bash
pnpm init
pnpm add @ctcstack/ctcdocs @ctcstack/ctcdocs-sync
pnpm add astro @astrojs/starlight sharp
pnpm add -D @astrojs/check @playwright/test eslint prettier typescript wrangler
```

`.npmrc`:

```ini
engine-strict=true
save-exact=true
strict-peer-dependencies=true
```

`.node-version` holds the Node major you build with — the deployment workflows
read it. Add a `pnpm-workspace.yaml` even though this is a single package, since
pnpm 11 reads its settings from there rather than from `package.json`:

```yaml
allowBuilds:
  esbuild: true
  sharp: true
  workerd: true
```

Without that, `sharp` never builds and image processing fails at build time with
an error that does not mention `sharp`.

### 2. Describe the deployment

`site.config.json` is the only place your project is named. Every key is
documented in [CONFIGURATION.md](CONFIGURATION.md); the minimum is:

```json
{
  "brand": {
    "name": "Example Corp",
    "siteTitle": "Example [DOCS]",
    "siteDescription": "Internal Example documentation",
    "faviconPath": "/favicon.svg"
  },
  "deployment": {
    "workerName": "example-docs",
    "environments": {
      "production": {
        "url": "https://docs.example.com",
        "visibility": "private"
      }
    }
  },
  "home": {
    "lede": "Every document here is published from Google Docs and is read-only."
  },
  "navigation": {
    "landingDocumentTitles": ["Overview", "README", "About"],
    "sectionIndexPages": true
  },
  "sync": {
    "generatedBy": "EXAMPLE DOCS SYNC",
    "commitBotName": "example-docs-sync[bot]",
    "defaultLocale": "en"
  }
}
```

`visibility` decides who may read the deployment and defaults to `private`.
Choose it deliberately now: the crawler rules, the response headers and the
boundary checks all follow it, and a mismatch fails validation rather than
reaching a deployment.

### 3. Wire up Astro

`astro.config.mjs` is a call to the preset:

```js
import { ctcdocsConfig } from '@ctcstack/ctcdocs/config';
import { defineConfig } from 'astro/config';

import siteConfig from './site.config.json' with { type: 'json' };
import { generatedRedirects } from './src/generated/redirects.ts';
import { generatedSidebar } from './src/generated/sidebar.ts';

export default defineConfig(
  ctcdocsConfig({
    siteConfig,
    sidebar: generatedSidebar,
    redirects: generatedRedirects,
  }),
);
```

`src/content.config.ts`:

```ts
export { collections } from '@ctcstack/ctcdocs/content';
```

**Those two imports do not exist yet.** The sidebar and the redirect map are
written by the first synchronization, and until then the build fails on a
missing module. Write them by hand so you can build today, and let the pipeline
overwrite them later:

```ts
// src/generated/sidebar.ts
// AUTO-GENERATED BY EXAMPLE DOCS SYNC. DO NOT EDIT.
export const generatedSidebar = [];
```

```ts
// src/generated/redirects.ts
// AUTO-GENERATED BY EXAMPLE DOCS SYNC. DO NOT EDIT.
export const generatedRedirects = {};
```

The first line is the ownership marker, built from `sync.generatedBy`.
Validation requires it on every file in a generated path, so a stub without it
fails the gate for a reason that has nothing to do with what you are testing.

### 4. The rest of the files

| File                   | What goes in it                                                                     |
| ---------------------- | ----------------------------------------------------------------------------------- |
| `public/favicon.svg`   | Your mark. Also probed by the access smoke test                                     |
| `public/robots.txt`    | `Disallow: /` for a private deployment; anything else for a public one              |
| `public/_headers`      | Cache and robots headers for `/*.md` and `/assets/generated/*`, matching visibility |
| `src/styles/brand.css` | The accent triad per theme. See [DESIGN.md](DESIGN.md)                              |
| `.gitleaks.toml`       | Secret-scanning allowlist, covering only paths Git never tracks                     |
| `tsconfig.json`        | Extends `astro/tsconfigs/strict`, includes `.astro/types.d.ts`                      |
| `eslint.config.js`     | `import { ctcdocsEslintConfig } from '@ctcstack/ctcdocs/eslint'` plus your ignores  |
| `prettier.config.mjs`  | `export { default } from '@ctcstack/ctcdocs/prettier'`                              |

`ctcdocs-sync validate` checks that `robots.txt`, `_headers` and `.gitleaks.toml`
exist and agree with your configuration, so run it early and let it tell you what
is missing rather than reading this table twice.

### 5. Scripts

The reusable workflows call your project by script name. Six of these are the
contract — `format:check`, `lint`, `build`, `test:search`, `test:ux` and
`deploy:dry-run`, plus `validate` through the installed command — and a missing
one fails CI with a message about a missing script rather than about whatever it
was going to check:

```json
{
  "scripts": {
    "dev": "astro dev",
    "build": "astro check && astro build",
    "preview": "astro preview",
    "typecheck": "astro check",
    "format:check": "prettier --check .",
    "lint": "eslint .",
    "validate": "ctcdocs-sync validate",
    "test:search": "ctcdocs-verify-search",
    "test:ux": "playwright test --config playwright.ux.config.ts",
    "deploy:dry-run": "wrangler deploy --env production --dry-run"
  }
}
```

`playwright.ux.config.ts` is a factory call, so the suites stay owned by the
platform and run against whatever corpus you have:

```ts
import { defineUxConfig } from '@ctcstack/ctcdocs/playwright';

export default defineUxConfig();
```

### 6. Build it

```bash
pnpm validate
pnpm build
pnpm dev
```

You now have the site, the navigation, the search index and the interface, with
an empty corpus. Everything after this point is about filling it and putting it
somewhere.

## Part 2 — the parts that need other people

Start these early; neither is fast.

### 7. The Google identity

Follow [GOOGLE_WORKSPACE_SETUP.md](GOOGLE_WORKSPACE_SETUP.md). You need a
Shared Drive, a Google Cloud project, a workload identity pool and provider
bound to your repository, and a service account that is a Viewer on the Drive
and has no roles anywhere else.

Then run a synchronization. The first one replaces the stubs from step 3.

### 8. Cloudflare

Follow [CLOUDFLARE_SETUP.md](CLOUDFLARE_SETUP.md) for the Worker, the custom
domain, and — for a private deployment — the Access application and its service
token. `wrangler.jsonc` is hand-written because Wrangler reads it itself;
`ctcdocs-sync validate` fails when its Worker name or custom domain disagrees
with `site.config.json`.

### 9. Workflows

Four thin callers, each pinned to a full commit SHA of this repository rather
than a tag — it is public, and these run inside CI that holds your deployment
credentials:

```yaml
# .github/workflows/ci.yml
name: Verification
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  verify:
    uses: ctcstack/ctcdocs/.github/workflows/project-ci.yml@<commit sha>
```

The other three are `project-sync.yml` (give it the schedule you want, plus
`workflow_dispatch`), `project-deploy.yml` (one call per environment) and
`project-rollback.yml`. Their inputs are documented in the header comment of
each file, and [DEPLOYMENT.md](DEPLOYMENT.md) lists the GitHub environments,
variables and secrets they read.

### 10. First deployment

[DEPLOYMENT.md](DEPLOYMENT.md) covers it, including the one-time bootstrap: a
brand-new hostname has no Worker binding yet, so the access preflight cannot
pass until something has been deployed to it once. Do that bootstrap with the
empty corpus, before any real content exists.

## When something is wrong

- **The build cannot resolve `./src/generated/sidebar.ts`.** You have not
  synchronized yet, and the stubs from step 3 are missing.
- **Validation says a generated file is missing its marker.** The stubs need the
  `sync.generatedBy` comment.
- **Validation objects to `robots.txt` or `_headers`.** They contradict the
  `visibility` you declared. The table in [CONFIGURATION.md](CONFIGURATION.md)
  says what each posture requires.
- **The access smoke test fails before the first deployment.** Expected on a
  hostname that has never been deployed to; see the bootstrap in
  [DEPLOYMENT.md](DEPLOYMENT.md).
- **Images fail to build.** `allowBuilds` is missing from `pnpm-workspace.yaml`,
  so `sharp` was never built.
